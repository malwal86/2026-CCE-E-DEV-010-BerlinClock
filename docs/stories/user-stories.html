1. How to read this document

The work is split into four features (A → B → C → D), each made of vertical user stories. Every story:

  • Is a full vertical slice: React UI → Spring Boot REST API → domain logic → PostgreSQL, and back. Nothing is built "backend first, frontend later".
  • Can be tested by a person: each story ends with a "Try it yourself" script. Start the app with docker compose up, use the screen, refresh the page or restart the stack to see the data persist, and optionally look at the table with psql.
  • Is also covered by automated tests written first (TDD), including a full-stack acceptance test against a real PostgreSQL (Testcontainers).
  • Builds only on earlier stories: you can stop after any story and still have a working, shippable application.

Each story page contains: the user story, why it comes at this point, acceptance criteria in Gherkin (using the exact kata examples), what changes in the UI, API and database, the tests to write in TDD order, and the "Try it yourself" script. The mini clock at the top right of each story shows what the UI can display after that story. The outlined row is the one the story adds, and faded rows are not built yet.

2. The Berlin Clock: rules and notation

The Berlin Clock (Mengenlehreuhr) shows the time with illuminated coloured lamps, read from top to bottom:

RowLampsEach lit lamp
Seconds lamp1 yellowOn for even seconds, off for odd
Five hours4 red5 hours
Single hours4 red1 hour
Five minutes11; every 3rd red (quarters), rest yellow5 minutes
Single minutes4 yellow1 minute

Lamps light from the left. Example: 16:50:06 = 3 × 5h + 1 × 1h, 10 × 5m + 0 × 1m, even second.

Text notation (from the kata)

CharMeaning
YYellow lamp lit
RRed lamp lit
OLamp off

The entire clock is a 24-character string, concatenated top to bottom:

Y    RRRO ROOO YYRYYRYYRYO OOOO
│    │    │    │           └ single minutes (4)
│    │    │    └ five minutes (11)
│    │    └ single hours (4)
│    └ five hours (4)
└ seconds (1)          → YRRROROOOYYRYYRYYRYOOOOO
Why the rows go top to bottom. The UI grows like the real clock, one row at a time from top to bottom, in the same order as the 24-character string. The seconds lamp is also the simplest rule, which makes it the right first story for setting up the whole UI → API → database pipeline.

4. Ways of working

4.1 Architecture: one vertical slice per story

Browser ─► nginx :3000 ─(/api/*)─► Spring Boot :8080 ───────────────────────────► PostgreSQL :5432
            │ React build            web          ConversionController, BerlinClockController,
            └ (Vite proxy in dev)                 ProblemDetail advice
                                     application  ConvertTime use case, ConversionHistory (port)
                                     domain       BerlinClock, Lamp, rows      (pure Java, no Spring)
                                     persistence  JdbcConversionHistory (JdbcClient) + Flyway migrations
  • Domain: pure Java, framework-free. All Berlin Clock rules live here and only here.
  • Database stores facts only (input time + when converted); the Berlin code is computed on read, so early history entries gain every row added later.
  • Ports and adapters: the use case depends on ConversionHistory; tests use an in-memory fake, production the JdbcClient adapter.

4.2 TDD cycle and commit convention

Outside-in per story: write the failing acceptance test first, then work inward (domain → use case → persistence → web → UI) with one red → green → refactor cycle per example. Each step is its own commit, and pushes happen only after green/refactor so CI stays green:

test(red):   five hours row lights one lamp at 08:23:00
feat(green): light one five-hours lamp per full 5 hours
refactor:    extract row-lighting helper shared by hour rows

4.3 Test strategy

LayerToolingWhat it proves
Domain unitJUnit 5, AssertJ, @ParameterizedTest + @CsvSourceThe Berlin Clock rules; every kata table row copied verbatim. 100% line/branch coverage enforced (JaCoCo).
Use caseJUnit 5 + in-memory ConversionHistory fake + fixed java.time.ClockSave / list / find / clear behaviour without a database.
Persistence adapter@JdbcTest + Testcontainers PostgreSQL 17 + FlywaySQL, mapping and ordering against the real database engine.
Web slice@WebMvcTest + MockMvcHTTP contract: status codes, JSON shape, Location header, RFC 7807 errors.
Acceptance (full stack)@SpringBootTest(RANDOM_PORT) + Testcontainers + RestClientThe story's acceptance criteria over real HTTP down to a real PostgreSQL, with nothing mocked.
UI componentVitest, React Testing Library, MSW, fake timersWhat the user sees: lamps, history, errors, live ticking.
Human testdocker compose up + browser (+ psql)The story's "Try it yourself" script on the real stack.

4.4 Definition of Done (applies to every story)

  • All acceptance criteria are covered by automated tests written before the production code (visible as red → green commits).
  • ./mvnw verify (needs Docker for Testcontainers) and npm run lint && npm test pass locally and in GitHub Actions.
  • Domain package at 100% line and branch coverage. Schema changes only through new Flyway migrations, never by editing an applied one.
  • docker compose up --build starts UI, API and database, and the story's "Try it yourself" script passes.
  • No conversion logic in the frontend. README updated if behaviour changed. Clean Code: clear names, small functions, no dead code.

Feature A · Story A2
Clear feedback for invalid times
Robustness
after A2 (no new row)
As a clock reader, I want a clear message when the time I type is not valid, so that I know how to correct it, and my history is not filled with junk.

Depends on: A1. Why now: every later story uses the same input, so the input contract is fixed before any more rules are added. Decision: 24:00:00 is rejected: the kata examples stop at 23:59:59 and java.time.LocalTime has no 24:00.

Acceptance criteria

Scenario Outline: Invalid times are rejected and not saved
  When  I convert "<input>"
  Then  the request is rejected as a bad request (HTTP 400)
  And   I am told: Invalid time '<input>': expected HH:mm:ss between 00:00:00 and 23:59:59
  And   "Recent conversions" is unchanged
  Examples:
    | 25:00:00 | hour out of range   | 1:2:3    | not zero-padded |
    | 24:00:00 | 24:00 not supported | 12-00-00 | wrong separator |
    | 12:60:00 | minute out of range | 12:00    | seconds missing |
    | 12:00:60 | second out of range | noon     | not a time      |

Scenario: The time is missing
  When  I convert with an empty field (or a request without "time")
  Then  the request is rejected (HTTP 400) and I am told: A time is required (HH:mm:ss)

Scenario: The UI shows the error and no stale result
  Given the result for 00:00:00 is displayed
  When  I convert "25:00:00"
  Then  the error is shown next to the input (announced via role="alert") and the old result is cleared

UI · API · DB

POST /api/conversions  {"time":"25:00:00"}
400 Bad Request   application/problem+json
{ "title":  "Invalid time", "status": 400,
  "detail": "Invalid time '25:00:00': expected
             HH:mm:ss between 00:00:00 and 23:59:59",
  "instance": "/api/conversions" }
DB: no row inserted.

Tests, in TDD order

  1. Acceptance: 25:00:00 → 400 problem+json; history count unchanged.
  2. Domain: DigitalTime.parse(String): strict HH:mm:ss (ResolverStyle.STRICT), one test per invalid example.
  3. Use case: invalid input never reaches the port (fake stays empty).
  4. Web slice: @RestControllerAdvice → ProblemDetail for invalid / missing time.
  5. UI: detail rendered in an alert; old result removed.

Database schema

-- V1__create_conversion.sql   (A1, the only migration planned)
CREATE TABLE conversion (
    id            BIGINT      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    time          TIME(0)     NOT NULL,
    converted_at  TIMESTAMPTZ NOT NULL
);
CREATE INDEX conversion_converted_at_idx ON conversion (converted_at DESC, id DESC);

Only facts are stored. Every Berlin Clock field is computed by the domain on read, so there is one source of truth and no stale codes. Ordering is converted_at DESC, id DESC, which stays deterministic when two conversions share a timestamp.

Appendix C · Scope, assumptions and decisions

In scope

  • The Berlin Clock rules from the challenge brief (stephane-genicot.github.io/BerlinClock.html), driven by the scenario tables of agilekatas.co.uk Feature 1, "Converting Digital Time to Berlin Time".
  • A React UI to convert a time, keep a persisted history of conversions and show a live clock, backed by a Spring Boot REST API and PostgreSQL.

Out of scope (deliberately)

  • Agilekatas Feature 2, "Converting Berlin Time to Digital Time". It is not part of the challenge brief. It is also under-specified: one seconds lamp only shows even or odd, so outputs like …YYYYYY → 23:59:59 cannot be derived from the lamps.
  • Users and authentication (the history is shared by everyone using the instance), editing conversions, pagination beyond the latest 50, cloud deployment, internationalisation.
  • Browser-automated end-to-end tests (Playwright/Cypress). Each story is verified by full-stack acceptance tests against real PostgreSQL plus a human "Try it yourself" script.

Decisions

DecisionRationale
Every story is a slice: UI → Spring → PostgreSQLA tester can verify each story by using the app, including persistence across refresh and restart.
Database holds conversion historyThe Berlin Clock calculation is pure. Storing what users converted is the natural, useful thing to persist.
Store input time + timestamp; compute the clock on readStore facts, derive the rest: one source of truth, no stale data, older entries gain rows as stories land.
PostgreSQL 17 + Flyway + TestcontainersProduction-grade engine, versioned schema, tests against the same engine as runtime (no H2 dialect drift).
Spring JdbcClient behind a ConversionHistory portOne small table: explicit SQL, no ORM magic. The port keeps the use case testable with an in-memory fake.
POST saves, GET reads; separate read-only GET /api/berlin-clockCorrect HTTP semantics (no side effects on GET). The live clock does not write to the database.
Live clock ticks not saved86,400 rows a day per tab would bury the real history.
Strict HH:mm:ss, 00:00:00–23:59:59Matches every kata example; 24:00:00 rejected.
RFC 7807 ProblemDetail; 503 when DB is downStandard errors; the user can tell "your input is wrong" from "our side is down".
Same-origin proxy (Vite in dev, nginx in Docker)No CORS configuration; the frontend always calls relative /api.
Red / green / refactor commits; 100% gate on the domainThe TDD process can be checked from git log; the gate is where 100% is meaningful.
